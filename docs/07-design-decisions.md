# 07 · 设计决策 · 坑 · 已知限制

## 1. 关键设计决策（ADR 摘要）

### ADR-1：`engine.ts` 不碰渲染层

**决策**：玩法逻辑与像素绘制彻底分离，`engine.ts` 一行 canvas 都不import。

**理由**：调平衡性（速度、开火频率）时不会误伤观感，调配色时不会改变玩法节奏。
早期把两者混在一个文件里，结果是改一个颜色都得跑一遍游戏确认手感没变。

**代价**：多一层 `Frame`接口（RGBA 像素）。可接受。

---

### ADR-2：坐标用「格」不用「像素」

**决策**：所有逻辑坐标的单位是**格**，只有渲染层才转像素。转换只在
`config.ts` 的 `cellX()` / `cellY()` 两个函数里发生。

**理由**：子弹的 `x` 是整数列号，命中判定退化成一行：

```ts
enemies.find(e => e.x === b.x && e.y >= b.y)
```

**子弹永远不会横向打偏**，"打空"这个概念从根上消失。

**代价**：所有速度都要换算（格/秒），多一层心智负担。

---

### ADR-3：开火时机由「停稳」决定，不是定时器

**决策**：`canTakeAction() = !ship.isMoving() && ship.canShoot()`。
飞船滑到列下 → 停稳 → 等冷却 → 开火 → 再拉下一个动作。

**理由**：这是"像在打游戏"而非"机器人扫掠"的核心。
定时器开火会让飞船边飞边突突，完全没有段落感。

**代价**：整局时长变长（要等停稳）。

---

### ADR-4：飞船匀速 + `min()` 夹住，**不做加减速**

**决策**：`Ship.animate` 用 `Math.min(x + dx, target)` / `Math.max(...)`，
加速度无穷大。

**理由**：曾经试过加梯形速度曲线（加速→巡航→减速）让运动更"物理"，
结果**观感反而更差**——因为减速曲线让飞船在列与列之间磨蹭，
失去了干脆利落的移动感，而且破坏了"停稳才开火"的节奏。

真人玩弹幕射击的操作感就是**匀速+ 急停**，这恰好是对的。

**代价**：起步和停车是直角。**这是刻意的。**

---

### ADR-5：等级用「用户自身分位数」而非绝对阈值

**决策**：把贡献数按分位数分档成 1~4 档，血量 = 档位。

**理由**：真实数据里绝大多数格子挤在低分位。早期用 `count // 5` 的绝对阈值，
结果整张图一片深绿（全是level 1），而且几乎凑不出高贡献格。

分位数分档保证**任何分布下都有 25% 的格子在 level 3 以上**。

**代价**：档位边界随每次输入数据变化，同一个格子今天 level 2、明天可能 level 3。
但因为整张图一起变，观感上无影响。

---

### ADR-6：`generateDummy()` 用 `crc32(username)` 播种

**决策**：不用字符串 `hash()`，用 `crc32`。

**理由**：必须让同一个用户名在任何机器上得到同一份假数据，
否则 `--seed` 失去复现意义（Python 的 `hash()` 每个进程带随机盐）。

⚠️ 移植到 JS 时同理：不能用 `Math.random()` 播种，
所以本项目用 mulberry32（见 `rng.ts`）。

---

### ADR-7：网络失败只能降级，不能抛出

**决策**：`fetchContributions` 任何失败都返回 `null`并打印警告，
绝不抛异常。

**理由**：构建流水线不该因为一次网络抖动就挂掉。降级到假数据，
至少能产出一份可看的GIF。

---

### ADR-8：GIF 共享调色板 + 关闭抖动 + 不设 `disposal=2`

**决策**：

1. 调色板**只量化一次**（首帧），所有帧共用
2. 脏矩形差分靠**透明索引**（`dispose: 0`）
3. **绝不设 `dispose: 2`**

**理由**：

- 每帧各自量化 → 色号在帧间漂移 → 播放时整片格子集体变色（"闪烁"）
- `dispose=2` 强制每帧全量编码 → **体积直接翻倍**

⚠️ 实测：减色数（32→16）只省 6%，画质明显变糙。
真正决定体积的是**帧数**。想压体积要减帧，不是减颜色。

---

### ADR-9：子弹穿透固定为 1

**决策**：`BULLET_PIERCE = 1`，每发只打掉一个格子。

**理由**：早期取 3（或 8），一发穿整列 → 飞船掠过即清、每列不必停，
射击感退化成一道激光扫过，**完全看不到逐格命中的反馈**。
取 1 后"高贡献格子要挨好几发才死"，贡献等级因此在观感上真实可见。

**代价**：整局帧数增加。

---

### ADR-10：默认策略是 `random`，不是 `column`

**决策**：CLI 默认 `-s random`。

**理由**：`ColumnStrategy` 是 `for week in range(52)` ——从第 0 周扫到第 51 周，
**一排一排推过去**。实测清场顺序严格单调递增（0,1,2,3,4,5…），观感机械。

`RandomStrategy` 取最近 8 个有目标的列，按
`同列10 / 1~3列100 / 4列以上1` 加权随机挑一个——其中 `4列以上权重=1`
是**意外感的唯一来源**（偶尔放弃近处跑去打远处）。

⚠️ 有专门的回归用例锁住这条（`test/strategy.test.ts`）。

---

### ADR-11：版本号单一来源

**决策**：版本只在 `package.json` 里写一次。

`CHANGELOG.md` 里不重复版本号，`README` 不写"当前版本"。

---

### ADR-12：绘制顺序敏感，不可随意调整

**决策**：固定顺序

```
星空 → 敌人 → 爆炸 → 子弹 → 飞船 → HUD
```

**理由**：照抄参考项目的 `GameState.draw()`。改顺序会改变遮挡关系——
比如爆炸画在敌人前面会盖住正在被打的格子。

---

### ADR-13：碰撞先移动后判定

**决策**：`animateBullets()` 里先 `b.y -= speed × dt`，再判定碰撞。

**理由**：反过来会"子弹停在格子边缘反复判定"。

---

### ADR-14：ship 出生在正中（第 25 列）

**决策**：`new Ship(Math.floor((COLS - 1) / 2))` = 25。

**理由**：52 列的正中。参考项目也是 `x = 25`。

---

## 2. 踩过的坑（按踩坑顺序）

### 坑 1：策略活锁 —— 17435 帧只开 33 枪

**现象**：`random` / `chaos` 策略跑 17000+ 帧几乎不开火，飞船在原地抽搐。

**根因**：给随机策略加了「已在飞子弹 >= 该列血量就跳过」的守卫。
当所有存活列都被判定为"子弹已够"时，`while` 循环空转、永不`yield`；
而子弹只在 `step()` 里才移动 → 状态永远推不动 → **死锁闭环**。

**修法**：去掉这个守卫。参考项目的 `RandomStrategy` 本来就没有它——
选中列后直接对该列最低的敌人打 `health` 发。

**教训**：反应式循环里，"跳过"逻辑必须保证最终能 `yield`，
否则就是活锁。

📌 回归用例：`不会死循环`、`都会真正开火`

---

### 坑 2：残留活靶 —— 打到最后剩 45 个

**现象**：`row` 策略清到剩 45 个就不动了。

**根因**：`genRow` 按 `maxHp` **快照**发动作，不看实时血量。
子弹串格/打空就会少发。

**修法**：改成读实时状态（和 `genColumn` 一样：比对总血量 vs 在飞子弹），
并在 `genActions` 末尾加兜底。

**教训**：动作流一旦开跑，局面就冻结了——任何基于"发时会算"的逻辑都可能失准。

📌 回归用例：`四种策略都能把场清空`

---

### 坑 3：恢复活靶后的帧上限 —— 剩 1 个打不完

**现象**：修完坑 2，从剩 45 变成剩 1，但仍不清完。

**根因**：`maxFrames` 自动推算时只算了开火冷却，**漏算了反应延迟**，
收尾阶段被截断。

**修法**：把`perShot` 改成按最坏值算（基准冷却 + 最大抖动 + 反应延迟 + 余量）。

**教训**：自动推算上限时，所有随机的成本都要按**最坏值**算，不能按均值。

---

### 坑 4：`score` 恒为 0

**现象**：击败数正常，但 `score` 一直是 0。

**根因**：先调`takeDamage()`（血量减到 0），再读 `victim.health` 算分——
读到的自然是 0。

**修法**：先记下打爆**前**的血量，再结算伤害。

**教训**：读一个会被即将执行的函数修改的值之前，先存快照。

📌 回归用例：`score 与击败数成正比`

---

### 坑 5：血量出现 hp40

**现象**：某些格子血量高达 40。

**根因**：参考项目直接用 GitHub API 返回的 `level`（0~4）当血量，
而我们 `data.ts` 拿的是**原始贡献数**（0~40），忘了分档。

**修法**：移植时补上按分位数分档（见 ADR-5）。

**教训**：移植时凡是"上游给了现成值"的地方，要确认我们的数据形态是否一致。

📌 回归用例：`血量只能 1..4`

---

### 坑 6：canvas 多边形边缘发虚

**现象**：飞船和敌人边缘有肉眼可见的渐变，比参考项目"虚"一号。

**根因**：PIL **不抗锯齿**，Canvas **会抗锯齿**。同一段多边形代码，
画出来的边缘不一样。

**现状**：**未修**。影响很小（实测每边差 1px 以内），
但确实存在。彻底修需要改用扫描线填充（`fillRect` 拼span）替代多边形。

**教训**：像素画从 PIL 迁到 Canvas 时，抗锯齿是个隐形差异。

---

### 坑 7：`gifenc` 在 ESM 下导不出具名导出

**现象**：`import { GIFEncoder } from 'gifenc'` 抛
"The requested module does not provide an export named 'GIFEncoder'"。

**根因**：gifenc 的 `package.json` 里 `main` 指向 CJS 构建，
Node 的 ESM 加载器对 esbuild 产出的 CJS（`__export` getter 形式）
探测不到具名导出。

**修法**：显式引`gifenc/dist/gifenc.esm.js`（它的 `module` 字段指向那个 ESM 构建）。

---

### 坑 8：`quantize()` 返回的不是 Uint8Array

**现象**：`raw.subarray is not a function`。

**根因**：gifenc 的 `quantize()` 返回普通 `number[]`。

**修法**：逐个拷贝进 `Uint8Array`。

---

### 坑 9：调色板结构理解错了两次

**现象**：`applyPalette() only works with 256 colors or less`。

**根因**：以为调色板是扁平字节数组，实际是 `[r,g,b]` **子数组的数组**。
`applyPalette` 检查 `palette.length <= 256`（是**颜色数**，不是字节数）。

**修法**：末尾多留一项当透明索引（GIF 的透明色要占真实槽位）。

---

### 坑 10：GIF 差分把三帧不变的像素误判为变化

**现象**：差分效果时有时无。

**根因**：拿"上一帧写入的缓冲区"（含透明占位）做基准，
而那个缓冲区里未变化的像素已经被写成透明索引了。

**修法**：单独维护 `prevReal` 保存**真实色号**，写入用另一个缓冲区。

**教训**：差分优化的基准必须是"真实状态"，不能是"输出状态"。

---

### 坑 11：转向时单帧速度跳变

**现象**：转向那一帧 `shipVx` 从 -4 跳到 +2.8，单帧 |Δv| = 6.8。

**根因**：检测到方向要变时，**同一帧内**就把 `shipDir` 翻了，
速度大小只降了 1.2 但符号翻了 → |Δv| = 2 × 速度。

**修法**：加"待执行方向"字段，先朝原方向减速，停稳了才换向。

（注意：这个修复随ADR-4 的匀速模型一起被移除了——匀速+ 急停本就没有这个问题。）

---

### 坑 12：测试自身写错

**现象**：`isMoving` 用例失败、`require is not defined`。

**根因**：

- 帧数少算一帧（4 帧 × 0.9375 = 3.75，从 5 走到 8.75，差 0.25 没到 9）
- ESM 里用了 `require`

**教训**：测试失败先怀疑测试。

---

### 坑 13：GIF 测试 OOM

**现象**：`SIGKILL`。

**根因**：GIF 测试对完整动画（2600+ 帧）编码了三次，全在内存里。

**修法**：改用 4 个格子的极小数据集。

**教训**：测试用的数据集要和产品数据集解耦。

---

## 3. 已知限制

| 限制 | 影响 | 规避方式 |
|---|---|---|
| 飞船边缘有抗锯齿渐变 | 观感略"虚" | 用 `fillRect` 扫描线填充替代多边形 |
| Canvas 抗锯齿也作用于圆角格子 | 格子边缘略软 | 同上 |
| 换fps 会改变观感 | `--fps 25` 和 `--fps 50` 观感不同 | 这是刻意的（ADR-2） |
| 无音效 | — | GIF 格式限制 |
| 不支持中文用户名 | 显示会缺字 | 点阵字体只有ASCII |
| `chaos` 策略很慢（5600 帧 / 280s） | 体积大（约 8.5MB） | 用 `random` |
| React Native 等非 Node 环境跑不了 | — | 需要 Node 22 |

## 4. 修改禁忌清单（Review 时请重点检查）

- ❌ **不要**把渲染逻辑写进 `engine.ts`
- ❌ **不要**在 `config.ts` 之外硬编码几何/颜色/速度
- ❌ **不要**把 `ship.x` 改成整数（会破坏匀速滑行的平滑度）
- ❌ **不要**把 `Bullet.x` 改成浮点（命中判定会失效）
- ❌ **不要**调整绘制顺序（见 ADR-12）
- ❌ **不要**把 `deltaTimeFor` 改成 `1/fps`（会改变整个节奏）
- ❌ **不要**在 GIF 编码里设 `dispose: 2`（体积翻倍）
- ❌ **不要**每帧单独量化调色板（会闪烁）
- ❌ **不要**把默认策略改成 `column`（观感变机械）
- ❌ **不要**用 `Math.random()`（破坏可复现性）
- ❌ **不要**在 `gif.ts` 里存`rgba.buffer` 之外的数据（会读到错位像素）
